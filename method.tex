This section presents our GPU porting approach, followed by our 
fine-grained data-management strategy designed to minimize host--device 
data movement.

LESGO contains nearly 300 loop nests, which makes rewriting all of
them as CUDA Fortran kernels difficult. It is also an extensive,
physics-validated codebase that its user community actively extends in
Fortran. Directive-based offloading preserves a single source tree, in
which the CPU build remains reproducible and serves as our correctness
reference. This approach also follows established practice in
atmospheric models~\cite{esclapez2025dales,lapillonne2014,govett2017nim}
and other production Fortran codebases~\cite{otero2019nek,caplan2019mas}.
We therefore port LESGO to GPUs with OpenACC directives and the NVHPC
compiler.

Porting LESGO requires us to decide both where each solver array
resides and where each routine computes. The two decisions depend on
each other. Every routine that stays on the host consumes solver state,
so the placement of computation determines which data must move between
host and device. In this section, we first compare data placement
strategies (Section~\ref{sec:method-placement}). We then decide where
each routine computes and which data moves at each host--device
coupling point (Section~\ref{sec:method-taxonomy}).

\subsection{Data Placement}
\label{sec:method-placement}

The solver state of LESGO consists of dozens of persistent 3D Fortran
arrays of $O(N_xN_yN_z)$ size, including velocity components, velocity
gradients, SGS stresses, and dealiased spectral scratch fields. Each
unnecessary host--device transfer therefore moves an entire field.
Directive-based ports commonly adopt the following data placement
strategies: CUDA managed memory, array mirroring, and fine-grained
explicit residency. The first two strategies require few
code changes, so we begin with them.

\vspace{0.08in}
\textbf{CUDA Managed Memory.} We first tried CUDA managed memory~\cite{caplan2023dc}, which
lets the driver migrate pages between host and device on demand and
requires the least porting effort. We build LESGO with
\texttt{-gpu=mem:managed} and run the production benchmark
(Section~\ref{sec:setup}) on 16 A100 GPUs. For this implementation,
\texttt{Nsight Systems} profiling shows that page faults and on-demand
data migration, which are inherent to demand-paged unified
memory~\cite{chien2019um}, stall execution and yield limited speedup
over the CPU version.

\vspace{0.08in}
\textbf{Array Mirroring.} Next, we evaluate array mirroring, which keeps
a device copy of every host array. We build LESGO with
\texttt{-gpu=mem:separate} and synchronize arrays with \texttt{update}
directives around each host routine. Mirroring works well when the
solver state fits comfortably in device memory and every kernel moves
to the GPU, so that data returns to the host only for diagnostics and
checkpoints~\cite{esclapez2025dales,giorgetta2022,xiao2025cales}. LESGO
does not fit this mold for two reasons. First, mirroring also
duplicates arrays that no kernel reads, which wastes device memory and
increases the number of GPUs a given grid requires. Second, several
routines run slower on the GPU than on CPUs. These routines should
therefore remain on the host.
Mirroring consequently transfers full fields at every step
wherever they consume solver state. 
On our reference configuration ($256^3$ grid with two
wind turbines on 4 A100 GPUs), \texttt{nsys} profiling shows that the
GPU computes for only 6\% of each time step, while host--device
transfers take most of the rest. In fact, these
transfers are largely wasted, because the host needs only a small part
of each array rather than the whole field.

Both evaluations show that achieving high GPU efficiency requires
fine-grained control over data residency and host--device transfer
footprints, which the third strategy provides.

\vspace{0.08in}
\textbf{Fine-Grained Explicit Residency.} This strategy lets the
developer decide, array by array and access by access, where each field
resides and which part of it moves between host and device. In OpenACC,
we declare every array that GPU kernels access as device-resident at
module scope (\texttt{!\$acc declare create}), so these arrays remain on
the device throughout execution. Every GPU kernel asserts data presence
(\texttt{default(present)}), so no data moves implicitly. Data moves
only at explicit \emph{coupling points}, where a host routine reads or
writes solver state. At each coupling point, we apply \texttt{update}
directives only to the array section that the host routine actually
accesses. Mirroring, in contrast, allocates a device copy of every array
and synchronizes full arrays around each host routine.

More importantly, this strategy does not require every kernel to run on
the GPU. Routines that suit the CPU better can remain on the host, as
long as they exchange only a small amount of data with the GPU. This
design has two advantages. First, each routine runs on the processor
that executes it faster, so the port benefits from both the GPU and the
CPU. Second, arrays that only host routines use stay in host memory,
which reduces the device memory footprint and lets a given grid run on
fewer GPUs than mirroring requires. The coupling points therefore depend
on where each routine computes, and we turn to this decision next.

present four treatments that minimize data movement for each class.

The structure of LESGO makes compute offloading straightforward. The
kernels that update the solver arrays are loop nests over $x$, $y$, and
$z$ whose iterations are independent. We therefore parallelize each
loop nest directly with an OpenACC \texttt{parallel loop} directive and
use its \texttt{collapse} clause to map the independent loop levels
onto GPU threads. We replace the FFTW~\cite{FFTW3} transforms of the
CPU build with batched 2D NVIDIA cuFFT~\cite{cufft} calls and bind them
to the same CUDA stream as the OpenACC kernels, so that transforms and
loops execute in order without host synchronization.

However, we found that not every routine fits this pattern. Some
routines carry serial dependencies, such as the pressure
zero-wavenumber recurrence. Others run better on the CPU, such as the
tabulated airfoil polar lookups, which involve irregular branching. In
addition, checkpoint writes require host I/O. We move a routine to the
GPU when it still exposes enough parallelism, restructuring it
if necessary (Section~\ref{sec:opt}). Otherwise, we keep it on the
host. Every routine that stays on the host reads or writes solver
state at the coupling point, so the placement of computation also
determines which data move between host and device.

We examine every coupling point along three axes: the spatial extent
the host routine touches (scalar, 1D column, 2D boundary plane, or 3D
subvolume), how often it executes (every step, periodically, or only
under a model option), and its access intent (read-only, write-only, or
read-modify-write). We then group and classify all coupling points in
LESGO into the nine classes listed in Table~\ref{tab:taxonomy}. For
each class, the table gives its concrete instance in LESGO, the
transfer cost that a naive port pays per step.

Working through the nine classes, we found that four treatments,
\emph{gate}, \emph{relocate}, \emph{slice}, and \emph{overlap}, suffice
to decide where and when each consumer runs and which data moves between
host and device. 
% Each exploits a different property of
% the coupling point, and we consider them in this order, moving to the
% next only when the previous one does not apply.

\vspace{0.08in}
\textbf{Gate} handles consumers that run only under a model option or
on a subset of steps. For example, only the CPU fallback of the SGS
model reads the velocity gradients, yet a naive port copies all
gradient fields to the host at every step, even when the selected SGS
model runs on the GPU. We wrap such a transfer in the same guard that
controls its consumer, so the transfer disappears whenever the consumer
does not run.

\vspace{0.08in}
\textbf{Relocate} exploits parallelism in the consumer. If the host
routine parallelizes well, we port it to the GPU so it can read
device-resident data in place. We apply
this to the time-integration and projection pipeline, the diagnostic
reductions, actuator sampling and force projection, and the distributed
tridiagonal chains. 

\vspace{0.08in}
\textbf{Slice} applies when the consumer should stay on the host, but
touches only a small part of a field. For example, the pressure zero-wavenumber
recurrence remains on the host, yet it
reads and writes only the DC column of the pressure field, about
1\,KB out of 34\,MB. We name only this array section in the
\texttt{update self} and \texttt{update device} directives.

\vspace{0.08in}
\textbf{Overlap} hides host computation that still run at every
step. For example, the airfoil polar lookups 
follow data-dependent branches and stay on the host. Their inputs are
fixed early in the time step, and the GPU does not need their outputs
until force projection. We launch the GPU kernels in between
asynchronously and run the lookups while they execute, which hides the
host time behind device execution.


The instances in Table~\ref{tab:taxonomy} come from LESGO, but the
same classes appear in other pseudo-spectral multiphysics
codes, providing a general porting checklist for similar solvers.
To illustrate how these strategies are applied, we present an example below.

\begin{lstlisting}[float=h,linewidth=\columnwidth,
caption={Structure-aware partial transfer in the
pressure solver. A 1D column transfer (bottom) replaces full 3D array
transfers (top).},label={lst:dc}]
! mirroring: full arrays around the host loop
!$acc update self(p, rH_z)          ! 2 x 34 MB
! serial loop along z on the host
!$acc update device(p)              ! 34 MB

! slice: only one column crosses PCIe, 1 KB
!$acc update self(rH_z(1:2,1,:), rbottomw(1:2,1))
do jz = 2, nz
  p(1:2,1,jz) = p(1:2,1,jz-1) + rH_z(1:2,1,jz)*dz
end do
!$acc update device(p(1:2,1,:))
\end{lstlisting}

% \vspace{0.05in}
Listing~\ref{lst:dc} shows the slice treatment in the pressure solver.
Each vertical column of the pressure array \texttt{p} forms an
independent system along $z$, and the GPU solves all columns in one
batched call. A single column cannot use this solver and is instead
computed by a serial loop along $z$ (Section~\ref{sec:bg-numerics}).
Each level of this loop depends on the level below it, and the
dependency continues across processes, because each process starts from
the top value of the process below. The loop therefore offers no
parallelism to the GPU, which would execute it slower than a single CPU
core, so we keep it on the host. A mirroring port synchronizes the full
\texttt{p} and \texttt{rH\_z} arrays around this loop, three full-array
transfers per step. The loop, however, reads only one column of
\texttt{rH\_z} and writes only one column of \texttt{p}. We therefore
name just these columns in the \texttt{update} directives, about
1\,KB each way. All other operations on \texttt{p}, including its halo
exchange with the neighboring process, run on the GPU, so the rest of
\texttt{p} never leaves the device. As shown in
Table~\ref{tab:finalmetrics}, profiling confirms that only minimal
host--device data transfer remains on the production benchmark.
