This section presents three optimizations that target structural
bottlenecks of the solver, followed by general practices from our
porting effort. Unless noted
otherwise, all performance measurements correspond to the 604M-cell
production case on 16 NVIDIA A100 GPUs (Section~\ref{sec:setup}).

\subsection{Chunk Pipelining across Serial Process Chains}
\label{sec:opt-tridag}

\begin{figure}[h]
    \vspace{-0.05in}
\centering
\includegraphics[width=\linewidth]{figs/fig4_lesgo_pipeline.pdf}
\caption{Pipelining the distributed Thomas solve. (a)~Sequential execution leaves processes idle. (b)~Chunking overlaps forward elimination (blue) with boundary transfers and back substitution (orange).}
\label{fig:tridag}
    \vspace{-0.05in}
\end{figure}

The spectral Poisson solve (\texttt{PoissonTridiag()} in
Algorithm~\ref{alg:step}) solves one tridiagonal system along $z$ for
each horizontal wavenumber pair. Under the slab decomposition, every
system spans all $P$ processes (Section~\ref{sec:bg-impl}). The Thomas
algorithm sweeps each system serially along $z$, so process $k$ idles
until process $k-1$ finishes its forward elimination, and back
substitution then returns down the chain in the same way.

To remove this serialization, we exploit the independence of the
systems. We partition them into $c$ chunks and pipeline the chunks
through the process chain (Fig.~\ref{fig:tridag})~\cite{povitsky1999,povitsky2000}. 
In the forward pass, process $k$ eliminates
chunk $m$, sends its boundary coefficients to process $k{+}1$ with
GPU-aware MPI, and immediately proceeds to chunk $m{+}1$. Process
$k{+}1$ meanwhile works on chunk $m$, so all processes compute
concurrently once the pipeline fills.
Moreover, with chunking, the last process starts back substitution for chunk $m$
as soon as it finishes the forward pass of that chunk, so the backward
wave of early chunks overlaps the forward wave of later ones.
Unlike reduced-system libraries that alter the elimination
arithmetic~\cite{laszlo2016,kim2021pascal}, our approach leaves the
inner Thomas loops untouched, so the results match the sequential
solve.

\subsection{Batching Many Small Work Items}
\label{sec:opt-batch}

In the solver, many components decompose into small, independent work
units. However, each unit is too lightweight to saturate the GPU on its own
and still incurs a fixed launch overhead. We batch these
units into fewer, larger device operations to amortize that overhead and
improve hardware occupancy.
We demonstrate this strategy with the actuator-line turbine model and the LASD subgrid-scale closure.

For the actuator-line model (\texttt{Turbines()}), a direct port
loops over the turbines and repeats the device uploads, kernel
launches, synchronizations, and small collective reductions for each of
them. Across the farm, this adds up to more than 1,000
\texttt{MPI\_Allreduce} calls per process at each step. We instead
treat the whole farm as one batch. The blade-point tables of all
turbines stay in device memory for the entire run. We then launch one sampling kernel
and one projection kernel that process the blade points of all turbines
together, and a single packed \texttt{MPI\_Allreduce} carries all
reduction quantities. These changes reduce the kernel launches and
collective calls per step by an order of magnitude and remove all
per-turbine device allocations.

The Lagrangian scale-dependent (LASD) subgrid-scale model (\texttt{UpdateLASDCoefficient()} in
Algorithm~\ref{alg:step}) has the same problem. Each coefficient update
filters 21 3D velocity and tensor fields at two test-filter scales. For
each horizontal plane, the filter applies a forward 2D FFT, damps
selected wavenumbers, and applies an inverse 2D FFT. A direct port
therefore launches thousands of single-plane FFTs per update, and none
of them is large enough to fill the GPU. We instead promote the 2D
scratch planes to 3D arrays, so that one batched cuFFT call filters all
vertical levels of a field at once. The thousands of launches become a
few dozen batched calls, and each call carries enough work to keep the
GPU busy.

\subsection{Heterogeneous CPU--GPU Execution}
\label{sec:opt-overlap}

As discussed in Section~\ref{sec:method-taxonomy}, not
every kernel suits the GPU. For example, blade-force evaluation in
the actuator-line model (\texttt{ComputeBladeForces()} in
Algorithm~\ref{alg:step}) runs \emph{slower} on the device than
on the host.
Each actuator point traverses a data-dependent path
through the airfoil polar lookup, causing warps to serialize.
Kernel-launch and data-transfer overheads also exceed the useful
computation. We accordingly keep this routine on the host.

\begin{figure}[h]
    \centering
    \includegraphics[width=\linewidth]{figs/fig_overlap.pdf}
    \caption{Heterogeneous overlap of the actuator-line model. }
    \label{fig:overlap}
\end{figure}

However, running this routine synchronously on the host would add
$\sim$28\,ms to every step and leave the GPU idle meanwhile. We avoid
this cost by decoupling blade-force evaluation from the GPU
work. The evaluation reads only the velocities produced at the start of the time
step, and the solver does not need its outputs until force projection
later in the step. The convection stage in between neither produces
its inputs nor consumes its outputs. We therefore split the
actuator-line model into two decoupled phases around convection
(Fig.~\ref{fig:overlap}). Phase~1 samples blade-point velocities on the
GPU, copies them to the host, and returns without waiting for the
device queue to drain. The CPU then evaluates blade forces while the GPU
runs convection. Phase~2 uploads the forces to the device and projects them onto the
grid. This decoupling removes host computation from the critical path,
saves $\sim$30\,ms per step, and raises overall GPU utilization to
\textbf{93\%}. The same approach applies to any host routine whose
inputs are fixed early in the step and whose outputs are needed only
later.

\subsection{Experiences Porting to Modern GPUs}
\label{sec:opt-impl}

Beyond the optimizations above, we identified three practices from
our porting effort that apply to directive-based GPU codes in general.

\vspace{0.08in}
\textbf{Compute Uniformly, Then Patch the Exceptions.} Branch
divergence within a warp forces a hot kernel to execute the divergent
paths serially. When the exceptional points form a lower-dimensional
subset of the iteration space, such as $O(N_xN_y)$ boundary cells
versus $O(N_xN_yN_z)$ interior cells, this penalty can be avoided. We
apply the interior stencil uniformly across the entire domain in a
single branch-free kernel with coalesced memory accesses, and
subsequently overwrite the boundary values with a second, substantially
smaller kernel. The redundant computation on boundary cells is
negligible relative to the volume computation.

\vspace{0.08in}
\textbf{Derive the Parallel Domain from the Data, Not the Loop Nest.}
A GPU kernel translated directly from a CPU loop nest inherits the loop
structure of the original code, which typically results in low
occupancy and strided memory access. We instead derive the thread
decomposition from the data layout. For regular stencil kernels, we
collapse all spatial loops with the contiguous index innermost, so that
each warp issues coalesced loads. For workloads distributed across many
small model instances, such as the turbines in
Section~\ref{sec:opt-batch}, we flatten all
instances into a single parallel domain and map each work item to one
thread, so that a single kernel exposes the parallelism of all
instances at once.

\vspace{0.08in}
\textbf{Align Code Structure with Compiler Offloading Models.} The
NVHPC compiler places small local arrays in thread-private local
memory, which resides in device DRAM and is substantially slower than
registers. We apply scalar replacement to these arrays, which allows
the compiler to promote them to registers.
% We treat the diagnostic output from \texttt{-Minfo=accel} as a mandatory 
% build check to verify that it does so. 
In addition, several Fortran utility functions in LESGO, such as the
complex-multiplication operator used in spectral differentiation,
return their result in a newly allocated array. Inside a GPU kernel,
each call to such a function therefore triggers a device memory
allocation, whose cost far exceeds the few arithmetic operations the
function performs. We manually inline these functions at their call
sites, so that each result is written directly into the target array
without any temporary allocation.
